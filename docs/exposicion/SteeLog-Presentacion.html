02 · El sistema

Por qué estas tecnologías y no otras

VS WPF · ELECTRON · WEB

Windows Forms

Buscábamos algo liviano: arranca rápido, usa poca memoria y corre en las PC de oficina del taller sin navegador ni servidor web.

VS .NET 8 · JAVA · PYTHON

C# y .NET Framework 4.8

La plataforma que domino y con la que nació la interfaz. Viene con Windows; dominio y aplicación en .NET Standard dejan abierta la migración.

VS SQL SERVER · MYSQL · SQLITE

PostgreSQL

El software que ya usaba la empresa trabajaba sobre PostgreSQL: se conservó el motor y los datos pasaron sin conversiones. Libre, transaccional y con bloqueo de filas.

VS INSTALACIÓN NATIVA

Docker

Versión fija, aislada y fácil de recrear para pruebas y demos. Con un PostgreSQL nativo solo cambia la cadena de conexión.

04 · Capa por capa

Dominio: las reglas viven en objetos que no conocen la base

  • Material — stock y mínimo no negativos, hasta dos decimales.
  • Recorte — una medida lineal, o ancho y altura; nunca ambas.
  • Movimiento — remito obligatorio, origen y destino válidos, al menos un ítem.
  • Orden de compra — la recepción es acumulativa y no supera lo pedido.
  • Conteo — solo se modifica mientras está abierto.
SteeLog.Domain/Inventario/SaldoInventario.cs
public static class SaldoInventario
{
    public static decimal Aplicar(
        decimal saldo, decimal delta)
    {
        decimal nuevo = checked(saldo + delta);
        if (nuevo < 0)
            throw new InvalidOperationException(
                "Stock insuficiente…");
        return nuevo;
    }
}

Un objeto inválido no llega a existir: el constructor lanza la excepción antes.

05 · El flujo central

El tipo de movimiento decide qué le pasa al stock

TipoImpacto
Carga inicial de inventario+ entrada
Compra+ entrada
Devolución de obra+ entrada
Envío a obra− salida
Venta de material− salida
Uso interno− salida
Compra eventual · Aporte de clientesin impacto
Registro internoajuste desde materiales

El impacto está guardado como dato en la tabla tipo_movimiento, no escrito en el código de cada pantalla.

Una compra eventual va directo a la obra: queda registrada y valorizada, pero nunca pasa por el stock del galpón.

Una sola función del dominio, ClasificadorMovimiento, resuelve el impacto para registrar, editar, revertir y calcular el Kardex.

06 · Integridad

Todo o nada: el stock se defiende en tres niveles

DOMINIO

Reglas

Saldo nunca negativo, cantidades con precisión fija y aritmética que detecta desbordes.

TRANSACCIÓN

Unidad de trabajo

Filas bloqueadas siempre en orden ascendente de ID, para que dos operaciones simultáneas no se traben entre sí. Ante un error, se deshace todo.

BASE DE DATOS

Restricciones

CHECK de stock no negativo, claves foráneas, campos obligatorios y 20 índices de acceso.

Si la conexión se corta justo durante el COMMIT, el sistema no adivina: avisa «resultado incierto» y pide verificar antes de reintentar, para no duplicar el movimiento.

07 · Otros flujos

Órdenes de compra y conteos: estados explícitos

Orden de compra

Se pide, y se recibe en una o varias entregas.

Pendiente→Recibida parcial→Recibida completa

Cada recepción suma al stock y deja una foto del saldo resultante. Solo una orden pendiente admite cambiar sus líneas.

Conteo físico

Se cuenta en el galpón y se compara.

Abierto→FinalizadooCancelado

Al finalizar se fija la diferencia contra el stock de ese momento. El conteo informa; no corrige el stock por su cuenta.

09 · Seguridad

Dos roles, y el permiso se verifica en el caso de uso

ROL

Administrador

Acceso completo: edita movimientos, crea órdenes, ve valorizaciones y configura reportes.

ROL

Galpón

Operación diaria: registra movimientos y recepciones. Precios y cantidades sensibles ocultos.

El inicio de sesión usa usuarios fijos de demostración. Es un adaptador reemplazable, no autenticación productiva.

  • Ocultar un botón no alcanza: cada caso de uso llama a Require(rol) antes de operar.
  • La sesión recordada se cifra con DPAPI, atada al usuario de Windows.
  • Todo el SQL es parametrizado.
  • La base solo escucha en 127.0.0.1.
09 · Seguridad

Saber quién cambió qué y poder volver atrás

BITÁCORA DE AUDITORÍA

La escribe la base, no cada pantalla

Un trigger genérico registra altas, cambios y bajas con el usuario que llega en la conexión. En un cambio guarda solo las columnas modificadas. La app suma los errores que vio el usuario, sin contraseñas.

COPIAS DE SEGURIDAD

pg_dump, verificadas y con red de seguridad

Manuales y automáticas al abrir la app, con ficha JSON y SHA-256. Restaurar exige escribir RESTAURAR, verifica la copia, hace una copia previa y restaura en una sola transacción.

Ambos módulos son solo para el Administrador. Si la bitácora falla, la operación del usuario sigue: la auditoría nunca bloquea el trabajo.

11 · Cierre

Límites conocidos y próximos pasos

Autenticación de demostración

Usuarios fijos. El puerto IAuthentication permite enchufar un proveedor real sin tocar las vistas.

Recepciones fuera del Kardex

Recibir una orden actualiza el stock, pero todavía no genera una línea en el historial del material.

Recortes duplicables

La base no impide dos recortes con el mismo material y medidas; hoy lo resuelve la aplicación.

Un puesto, una base local

Pensado para un equipo. La arquitectura admite mover la base a un servidor cambiando la configuración.
